M31表单通知与邮件通道

所属路径 C 第 31 / 31 讲 S9 通知与触达
留言进来了，怎么让它在 1 分钟内找到人
学完能独立配通一条发信通道，并用四条证据证明它真的能送达

01为什么重要

表单是黑洞：留言进了库，但没人知道，等于没收。通知通道是「后台从数据变成消息」的那一步，也是第一次把外部服务的凭据接进系统——这一步凭据怎么摆，决定了以后「改个通知邮箱」会不会变成「交出公司发信权」。

02要讲清的 5 件事核心要点

  • 两个角色必须分开：收件人（谁该收到）在后台改、即时生效；发信账号（用谁的名义发）在服务器环境变量里 —— 凭据放进后台面板，等于把「冒充公司发信」的能力交给任何一个后台账号
  • 客户端专用密码 ≠ 网页登录密码：账号开了「安全登录」后，用网页密码连 SMTP 一定失败
  • 535 Authentication failed 是通用认证失败码，不能反推原因。判据是「账户安全」里那行按钮显示「已开启」还是「需先绑定微信」，不是报错码本身
  • 改配置只替换 MAIL_* / SMTP_* 那几行，别整文件重写 —— 否则 SITE_NAME 这类含空格的值会被改坏；改前备份、改后重启并回读自检
  • 验证要四条证据：后台状态灯、测试邮件、真实留言链路（含「点回复，收件人应是访客填的邮箱」）、日志里的 [mail] 已通知 N 位收件人

03照着做：6 步操作顺序

  1. 建一个专用发信账号（别用个人邮箱），设好显示名——这是收件人看到的发件人
  2. 登录该账号，确认 SMTP 已开启，生成「客户端专用密码」并保存
  3. 先看「账户安全」那行按钮状态，判断到底该用哪种密码
  4. 在每台服务器跑一次配置命令，只替换 MAIL_* / SMTP_*，脚本会备份并重启回读
  5. 后台看状态灯 → 发测试邮件 → 到联系页真发一条留言，确认「点回复」指向访客邮箱
  6. 出问题先查 journalctl 里的 [mail] 记录，再对着故障对照表定位
# 1) 先在邮箱后台建专用发信账号、开 SMTP、生成「客户端专用密码」
# 2) 每台服务器跑一次（脚本只替换 MAIL_* / SMTP_* 那几行）
sudo bash /opt/<站点>/repo/deploy/setup-mail.sh \
  smtp.exmail.qq.com 465 msg.website@你的域名 '客户端专用密码'

# 3) 排障：先看日志，再对着故障对照表定位
journalctl -u <服务名> -n 80 --no-pager | grep -i mail
nc -zv smtp.exmail.qq.com 465

04产出物与验收做完怎么算过

产出物

一条能送达的发信通道 + 一份「收件人 / 发信账号」职责边界说明 + 故障对照表

验收判据

可验后台状态灯显示「已配置发信通道」，测试邮件与真实留言都能收到，日志里有 [mail] 记录
人评能说清「为什么发信账号不放后台」，并解释 535 的两种成因怎么区分

05练习15 分钟内可做完

故意用网页登录密码去配 SMTP，先撞出一次 535；然后不看报错码，去「账户安全」看那行按钮的状态判断是哪种原因，再换成客户端专用密码修好。

06最容易踩的坑

把 535 一律当成「缺客户端专用密码」，照着这个结论反复重生密码
后果：留言躺在库里没人知道，客户等三天没回音；更糟的是反过来——为了「方便」把邮箱密码填进后台面板，此后任何一个后台账号都能拿它对外发信。

08本讲术语全部 28 条

  • v1 / v2 后台：本项目自造的阶段叫法。v1 = 纯静态站；v2 = 加了内容管理后台（登录、数据库、上传）。不是技术名词。
  • 台账：只记「有什么、什么时候到期、谁负责」的清单；密钥台账不记密钥本体。
  • 发信账号 / 收件人：发信账号＝真正把邮件发出去的那个邮箱，配置在服务器环境变量里；收件人＝谁该收到通知，在后台改、即时生效。两者刻意分开：一个管凭据，一个管日常运维。
  • 客户端专用密码：开启「安全登录」的邮箱账号，供 SMTP / IMAP 这类第三方客户端使用的独立密码。和网页登录密码不是一回事，混用会一直报 535。
